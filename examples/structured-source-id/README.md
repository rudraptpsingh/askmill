# Installed a4 source-ID integration fixture

This fixture uses the published **AskMill 0.1.0a4 wheel**, SHA256
`6a17f43435df1fd9388331903b2383d4f8fb94ffd48e3fc2acafc4be2edb2745`.
It starts a loopback HTTP stub with canned responses, executes the installed
`askmill run --request` CLI and retains real runner outputs/receipts. It performs
no model inference, downloads, GPU work or producer edits. The stub uses a
separate synthetic lease; real inference must use every configured host lease.

Run with the Python from an environment installed from that wheel:

```sh
/path/to/a4-env/bin/python examples/structured-source-id/verify.py \
  --wheel /path/to/askmill-0.1.0a4-py3-none-any.whl \
  --output /workspace/private/new-fixture-output
```

The script rejects a different wheel, modified installed Python modules, a
different CLI version or an existing output directory. It writes `summary.json`,
the forwarded `wire-requests.json`, and each case's exact request/stdout/stderr
and receipts. Replay makes no additional provider generation call. There are
four synthetic generation calls in total; both request rejections send none.

| Case | Exit | `status` | `complete` | `response_validation.valid` |
|---|---:|---|---|---|
| Success and replay | 0 | `completed` | true | true |
| Out-of-scope output ID | 4 | `schema_invalid` | true | false |
| Truncated malformed JSON | 3 | `incomplete` | false | false |
| Truncated but valid JSON | 3 | `incomplete` | false | true |
| Unsupported `pattern` schema | 2 | `invalid_or_unavailable` | absent | absent |
| Wrong schema SHA256 | 2 | `invalid_or_unavailable` | absent | absent |

Every model-result case retains literal text and the raw provider response,
including invalid/truncated output. Request rejections return `error` and have
no inference receipt. No repair, retry or fallback occurs. The four model cases
have acknowledged settlements, reaped workers and no quarantine. Each case has
an isolated receipt store because different canned answers to the same request
must not reuse an earlier cached result. Their cache keys can therefore match.

## Request and command

[request.json](request.json) is a complete `askmill.request.v2`, with two synthetic
source parts and a closed response schema. Success text is exactly
`{"source_id":"part-a"}`. [source.txt](source.txt) has SHA256
`bef7cf48e301ce1fbb44f8763d7fc4f5da7cf7c7951c77b8c46ef6fd62f2e214`.
The schema pin is
`84dc641a7cadaaf4951d7d7f5fcb940eaff4ce4da1a43a5fedf5a618cbb24af5`.
Compute schema pins with `ResponseSchema.from_schema(document)`; the JSON CLI
receives its `schema_version`, `document` and `sha256` envelope.

The actual production-facing command shape is:

```sh
/path/to/a4-env/bin/askmill --config /host/pinned-profiles.json \
  --store /workspace/private/receipts \
  run --profile YOUR_PINNED_PROFILE --request /workspace/request.json
```

That configuration must declare the complete shared `lease_paths`. The stub
configuration generated by this fixture is temporary and its server closes
after verification. Do not point production work at it. The host's default
launcher may still be a3; use the explicitly installed a4 executable.

## Exact result and receipt API

The full success result is `OUTPUT/success/stdout.json`. It is
`askmill.result.v2`; `text` contains a JSON **string**, and schema validation is
in `response_validation` (`askmill.response-validation.v1`, `schema_sha256`,
`valid`, `errors`). There is no parsed `data` field or root `schema_valid` field.
The SDK can read the same CLI output:

```python
import json
from pathlib import Path
from askmill import Result
from askmill.runner import digest

case = Path("OUTPUT/success")
result = Result.model_validate_json((case / "stdout.json").read_text())
assert result.schema_version == "askmill.result.v2"
assert result.complete and result.response_validation.valid
selected_id = json.loads(result.text)["source_id"]

receipt = json.loads(
    (case / "receipts" / (result.receipt_id + ".json")).read_text()
)
content = receipt["content"]
assert digest(content) == receipt["sha256"]
assert content["key"] == result.receipt_id
assert content["schema_version"] == "askmill.receipt.v2"
assert content["request"]["response_schema"]["sha256"] == result.response_validation.schema_sha256
assert content["raw_response"]["message"]["content"] == result.text
assert result.domain_acceptance == "unverified"
```

Receipt `content` also includes `profile`, `runtime` and `result`. Settlement is
separate: `receipts/settlements/{result.session_id}.json`, with the same outer
`content`/`sha256` integrity envelope. Inspect `worker_reaped`, `quarantined` and
`external_request_settlement`; a result alone does not establish cleanup.
Replay retains the original attempt/session identifiers. A new replay session
also produces its own settlement; do not infer current ownership from a cached
result's original session ID.

AskMill freezes the caller-supplied `sources` hash; it does not open or approve
that source. PDF2Data must rederive the actual source scope, membership, roles,
coverage and literals. `part-b` is also schema-valid here but would fail the
fixture's condition-selection expectation. Neither JSON validity nor a canned
stub answer establishes semantic acceptance. Keep partial/failed results and
source holds; only a completed, schema-valid candidate advances to independent
consumer checks. Repeating an identical failed request in the same store
replays it; retries require an explicit changed request/budget.
