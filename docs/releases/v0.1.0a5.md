# v0.1.0a5: bounded input and bound replay

## Confirmed issue and scope

Actual PDF2Data rc10 request-envelope controls showed that a4 accepted duplicate
JSON keys and repeated source IDs. Source counts and aggregate input bytes had
no total limit, and checksum-consistent replay mutations could contradict the
result/model/session bindings. This release fixes those four owning-boundary
defects. It does not add a host authorization engine, model benchmark or source
acceptance. Historical receipts and package versions remain unchanged.

## Changes and contract pins

Runner-owned raw JSON boundaries reject duplicate keys and non-finite constants
before typed validation: SDK `model_validate_json`, CLI request/batch/config,
profile files, worker messages, HTTP responses and receipt files. Once another
framework has parsed JSON, lost duplicate-key information cannot be recovered;
MCP/host framing parsers own their original byte boundary.

Both existing request versions now reject repeated source IDs, more than 128
sources, source IDs over 300 characters or references over 4096 characters.
Resource budgets: request JSON 4 MiB, batch JSON 8 MiB, source metadata 512 KiB,
frozen aggregate input/HTTP request body 32 MiB, receipt read 96 MiB. The frozen
input budget includes base64 image bytes. These are admission/resource bounds,
not measured latency thresholds. Existing image/token/schema/deadline limits
remain. Rejections preserve input/old receipt bytes and never trim them to fit.
Object admission uses compact sorted ASCII-escaped JSON sizes; raw file/body
limits also check actual bytes before parsing or sending.
Referenced original files are not opened by the generic runner; their byte
budgets and source authorization are still the source-owning consumer's gates.

Wire fields and request/result v1/v2 names stay unchanged. a5 tightens admission;
its released request/batch schema hashes explicitly differ from a4. Consumers
must pin the new wheel and its schema hashes when adopting the new limits.
Existing jobs must continue using their original package/schema pins.

Replay verifies the immutable input key, profile, runtime, model/revision,
receipt ID, canonical attempt/session IDs, response schema and raw response
bindings. Prior sessions require an integrity-checked, matching acknowledged
settlement. Missing/unconfirmed cleanup is refused. The current live session
may reuse only its exact in-memory committed receipt checksum; it need not
pretend an already closed settlement exists.

New `askmill.settlement.v2` binds the profile hash, sorted absolute lease-path
hash and runner version. Runtime identity now pins runner version and
runner/contract/JSON implementation hashes plus lease-path hash. Consequently
a5 has a new cache identity; it never rewrites old keys to force reuse. A parent
crash can leave an immutable committed item without a settlement; preserve it
but refuse replay rather than infer safe cleanup from its existence.

## Validation and adoption

Qualification uses the actual frozen CERC request and recorded completed and
failed receipts, with envelope-only refusal mutations and zero model calls.
Controls verify original bytes remain unchanged. Real data stays outside the
public repository; optional environment-driven tests consume an authorized
receipt path. Public contract-artifact and historical software controls are not
document coverage or accuracy cases. Installed-wheel results, CI and checksums
are recorded in immutable release assets after those checks pass.

The current source/customer holds remain: semantic acceptance unreviewed,
dependencies unbound, source quality requiring repair, Serentica reviewed:false.
Host permissions/revocation and source/numeric/legal acceptance stay with the
consumer. Fresh HTTP wire-byte/stage/replay timing instrumentation and a matched
real performance baseline remain separate gaps; a5 does not claim a p95/pass.
Consumer readoption is pending explicit installation and acceptance.
