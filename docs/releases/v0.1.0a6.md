# v0.1.0a6: complete-request MCP and producer identity

Central's actual installed-a5 stdio probe found that flat `run` could not carry
the source metadata in the real request-v2 CLI object. Existing `run_batch`
already supported full requests. Initialize also reported SDK 1.30.0 instead
of the pinned AskMill application version.

a6 adds `run_request_v1` using the same `Request`, profile, leased Session,
receipt and output path as CLI `--request`. The existing two tools remain.
Unknown top-level arguments are rejected for all tools, with bounded argument
validation and concise gate errors before a session. Initialize now advertises
the application version; the versioned JSON producer resource separately
exposes SDK identity. Exact contracts and usage are in [MCP.md](../MCP.md).

Actual real-request admission/refusal controls use a guard that raises before
inference; no fake provider result is substituted. Full request and batch
metadata reach that guard unchanged, including source hashes, while invalid
input reaches no session. The source suite passes 86 checks with one optional
skip when both authorized external real-request/receipt inputs are supplied.
These software/control counts add no document accuracy or generation cases.

An SDK 1.12 lower-bound probe failed its own import with Pydantic 2.14. a6
therefore sets the optional MCP extra to the tested `mcp>=1.30,<2`; the isolated
environment passes after upgrading that SDK. Previous environment and release
bytes stay unchanged. The new wheel, installed checks, schema/module pins and
main CI are recorded in immutable release assets after qualification.

Consumer adoption is pending explicit acceptance. The qualified change is
metadata/identity and admission/refusal parity, not live source-bound model
generation, cache migration, full pipeline acceptance or legal/source approval.
No host authorization logic or model benchmark is added. Current source,
unresolved-context and reviewed:false client holds remain consumer-owned.
